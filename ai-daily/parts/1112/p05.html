深读 · 四道闸拦住的不是恶意 第 05 版 / 共 16 版

OpenRouter 在 11 月 12 日给 Agent SDK 加了一组防护，针对的是智能体最平常、也最烧钱的一种失败：反复调用一个失败的工具。模型并没有变坏，只是没有任何东西告诉它「可以停了」厂商口径。

先把这个失败讲清楚。工具报错、参数没改、模型再试一次——这是重试逻辑最自然的写法，问题在于每一轮都会把整段对话连同历史一起重发，于是下一轮比上一轮更贵。循环里没有退出条件，也没有预算概念；放着跑一夜，账单可能是四位数的美元公开报道。本报把它叫 死循环模型不断重复同一组工具调用且没有退出条件。它不需要任何恶意，只需要一个一直失败的工具和一个没有上限的循环。：它不需要模型有任何恶意，只需要一个一直失败的工具和一个不会自己停的循环。

OpenRouter Agent SDK 的四道闸，各自拦的是什么
闸拦的对象属于哪一层没写清楚的部分
死循环检测整体是否在原地打转调用序列判定阈值与误报率未公布
重复调用规则同一工具、同一参数反复出现单次调用参数略有变化是否算重复
步数上限一次任务最多走几步任务级上限默认值与可调范围未公布
成本上限一次任务最多花多少钱任务级按什么币种、含不含重试计费

官方给出的测试结果很短：在 6 个模型上测过，开启防护后模型在第三次重复调用被正确拦下，避免了意外的高额 API 支出厂商口径。本报没有独立复现这组数字，也不把它读成「所有循环都能拦住」——它说明的是这一组测试里的一种特定重复。官方同时说明，技术细节与推广计划尚未公布公开报道。四道闸的清单是公开的，闸的高度目前不是。

为什么这条值得放深读。过去一年，智能体出事的叙事都围着「越权」「越界」转，于是防护也多写在权限那一侧。但真实生产环境里最先烧掉预算的，往往是这种既不越权、也不恶意、只是停不下来的循环。把「停」做进 SDK，意味着责任从「让模型更聪明」转到「让调用层有边界」。这与第 03 版把界面交给应用画，是同一种思路：不指望权重解决问题，用代码把上限钉死。

还有一个容易被跳过的点：拦错了怎么办。四道闸里任何一道误判，都会把一个本来快完成的任务砍断。步数上限和成本上限尤其如此——它们可靠，正是因为它们粗暴。发布材料目前没有说明被拦截后是返回可恢复状态、还是直接终止，也没有说明误报如何观测公开报道。一道会误伤的闸，需要配套一条「怎么申诉」的路径；否则团队第一反应会是把它关掉。本报把这一条记进第 15 版的观察清单，等后续文档补上。
