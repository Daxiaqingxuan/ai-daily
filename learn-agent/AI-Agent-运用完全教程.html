这门课怎么学

先说清楚它不教什么，以及为什么你需要的不是「更会说 prompt」。

市面上大多数 agent 教程在教「怎么写提示词」：给角色、给示例、链式思考、少样本。这些你其实已经会了——你能写出十二段、几千字、带硬检查清单的自动化提示词，能把版式规范从 v1 迭代到 v6，能让 agent 直接装 JDK、编 APK、改桌面快捷方式、发布站点。这是相当靠后的水平。

但你这几天也反复遇到同一类麻烦：报纸从 9 版改到 15 版靠一轮轮「感觉少点什么」；规范里写着的自洽硬检查，实际还是靠人眼截图；[hidden] 被 CSS 覆盖这种 bug 要等看到截图才发现；自动化把报纸存到错误目录，两端就都读不到；改了六版却没有一个能回滚的版本。

这些不是提示词问题，是工程闭环问题。所以本教程的主线是：

把「让 agent 把活干出来」升级成
「让 agent 的活能被机器检查、能被回滚、能无人值守地重复跑」

为什么这样安排 一次性交付时，人眼验收就够了，所以你感觉不到缺口。一旦进入「每天 8 点自动出报、两端自动同步」，人不再在回路里，所有含糊的规则都会变成静默故障。你的项目正好走到了这个拐点，所以现在学这些，收益是立刻可见的。

怎么用这套材料

  • 教材：本文件，8 章 + 4 附录，可离线打开，建议按顺序读第 0→2 章，后面按需要查。
  • 模板：templates/AGENTS.md，可直接拷进项目当「项目契约」。
  • 可运行示例：examples/validate.py，已在你的 ai-daily/ 上实测 32/32 通过，并做过变异测试（故意删一条锐评 → 立刻报错并退出 1）。
  • 练手对象：就用 ai-daily/。它已经有自动化、规范文档、多端产物、真实故障案例，是一个完整闭环样本，比另起一个玩具项目学得快得多。

每章末尾有「本章自检」，全是是非题。答不上来就回头重读那一节，别往下赶进度。

CHAPTER 0

地基：agent 的四个性质，推出四条铁律

这一章是整本书的地基。后面所有做法都是从这四条性质里被逼出来的，不是行业习惯，也不是仪式感。

先拆掉一个误解

agent 不是「更聪明的聊天框」，也不是「会自己思考的同事」。从工程上看，它是：

一个无状态的、概率性的、能调用有副作用工具的循环函数

拆成可观察的形式就是：

context = 任务描述 + 历史 + 工具返回
while 未完成:
    action = model(context)        # 模型只负责「下一步做什么」
    result = execute(action)       # 外壳负责真的去做（读文件 / 跑命令 / 发请求）
    context += (action, result)    # 把结果追加回上下文
    if action 是 finish: break
模型只提议，外壳才动手；循环靠「把结果写回上下文」推进

这个视角很重要：模型不执行任何东西，它只输出文本；真正改文件、发请求的是外壳。所以「agent 会不会搞破坏」这个问题，答案取决于你给外壳开了什么权限，而不是取决于模型多聪明。

四个性质 → 四条铁律

性质它必然导致什么你必须做的（铁律）
无状态
每次会话从零开始		「上次说过」等于没说过；换个会话、换个自动化，约定全部丢失约定必须落在文件里（第 1 章 AGENTS.md），不能靠对话记忆
上下文有限且会衰减
越长的输入越顾此失彼		几千字 prompt 里，后面的排版细则会压过前面的内容纪律；144KB 样板会把任务本身淹没把信息分层、按需加载，唯一真源，参考材料与指令分离（第 1 章）
概率性输出
同样输入不保证同样结果		这次 15 版 15 锐评都齐，下次可能少一条；「看起来没问题」不可靠验收标准写成可执行断言，跑不过就带错误重试（第 2 章）
工具带副作用
能覆盖、删除、对外发布		一步走错会污染真源、把半截文件当成功、把未校验内容推到线上最小权限 + 备份 + 原子写 + 幂等（第 4、5 章）
在你项目里 你这四条全踩过：约定散在日志 / 提示词 / 规范三处 → 自动化把报纸存错目录（无状态）；12 段提示词 + 144KB 样板 → 每期要整份重读（上下文）；「自洽硬检查」写在规范里却没代码 → 靠截图发现 [hidden] 被覆盖（概率性）；重新发布、生成快捷方式、改自动化提示词都是不可逆动作（副作用）。所以后面 8 章不是新知识，是把你已经遇到的坑，系统地堵上。

由此得到一句总口诀

凡是不能被机器检查的交付，就等于没有交付标准。

人眼验收只适合「一次性、有人在场」的场景。你已经有两条每日自动化，人不在回路里，这句话就从建议变成了硬要求。

本章自检
  • 能说清「模型输出」和「外壳执行」的分工，以及为什么权限问题属于外壳。
  • 能对着自己任一个项目，指出四条性质各造成了哪一个具体麻烦。
  • 能解释「为什么要写验收脚本」，而不是回答「因为大家都这么干」。
CHAPTER 1

上下文工程：把「给模型看什么」当成设计对象

长 prompt 不是越强越好。这一章讲怎么把信息分层，让agent 每次只看到它需要的那部分。

长 prompt 的三个失效模式

  1. 指令稀释：约束从 5 条涨到 50 条，每条的权重都在下降。你写了 5 条自洽硬检查，模型在生成 15 版正文时很容易顾不上第 4 条。
  2. 自相矛盾：文档迭代多次后，旧段落和新段落同时对同一件事给出不同要求。你的版式规范从 v1 到 v6 改了 6 次，章节编号出现过两个「第 13 节」——人或模型读到都会含糊。
  3. 参考材料淹没任务：把 144KB 的完整样板 HTML 塞进上下文，只为复用其中一段 CSS。绝大部分 token 花在不会变的内容上，真正要写的正文反而成了少数派。
关键认知上下文不是「越多越好」，是「信息密度越高越好」。每加一段材料都要问：这段在本次任务里会改变模型的决策吗？不会，就别放进本次提示词。

三类信息，必须分开存放

类型特征放哪怎么给
不变量几个月不变：路径、口径、命令、禁令AGENTS.md（项目契约）每次会话开头读一次，短
参考样例大、少变：CSS 骨架、图表模板、样例报纸独立文件 reference/按需引用，或由脚本直接拼装，不进提示词
本次任务每次都变：今天要什么、哪里改了对话 / 自动化提示词越短越好，只写差异

唯一真源原则：同一件事只在一个文件里说。要改，改那一处。你现在把「报纸存哪」同时写在自动化提示词、工作日志和我的记忆里，任何一处过期就会分叉——主自动化存错目录就是这么来的。

落地动作一：写 AGENTS.md

这是「给 agent 看的 README」，和你写给人看的 README 不一样：不介绍项目多好，只写会出错的地方。配套模板已经写好，结构是固定的七节：

# 项目名 · 项目契约
## 1. 路径（唯一真源，最容易出错，写最前）
## 2. 不变量（改代码不得破坏）
## 3. 常用命令
## 4. 交付流程（顺序不可换）
## 5. 验收（跑什么、什么结果算过）
## 6. 本机环境事实（别让 agent 重复踩）
## 7. 明确禁止
在你项目里模板里第 6 节已经把你踩过的坑固化了：COM 被安全策略拦、--window-size=390 假象、sharecode cookie、PyPI 源、发布同意不跨轮。这些以前每次都要重新试一遍，现在读文件就知道。

落地动作二：把 144KB 样板拆开

当前出报是「模型读整份样板 → 输出整份新报纸」。改成三段式：

reference/style.css      ← 不变的 CSS，脚本直接读入
reference/skeleton.html   ← 只剩结构占位符 {{BODY}} {{ISSUE}} {{DATE}}
本期正文片段.md           ← 模型只写这个，体量从 144KB 降到几十 KB
build.py                  ← 拼装 + 校验 + 落盘，模型不参与

好处不只是省 token：模型再也不可能把 CSS 改坏，因为它根本看不到 CSS。这就是「用结构约束代替口头约束」——比在提示词里写十遍「不要改样式」有效得多。

落地动作三：渐进披露

不要一开始就把全部规范塞进去。先给目录和摘要，等 agent 要写某一版时再给那一版的细则：

第 1 轮：AGENTS.md + 任务一句话 + 「需要细则时读 reference/版式规范.md 第 N 节」
第 2 轮：agent 自己按需打开对应章节
第 3 轮：交付前跑 validate.py
动手练
  1. 把 templates/AGENTS.md 拷到 ai-daily/，按实际改一遍路径表。
  2. 数一数：现在「报纸保存位置」这句话在几个文件里出现？把它们改成只指向 AGENTS.md。
  3. 把 11-04 样板里的 <style> 块抽成 reference/style.css，验证浏览器打开仍正常。
本章自检
  • 能区分不变量 / 参考样例 / 本次任务，并说出各自该放哪。
  • 能解释「为什么把 CSS 抽走比写十遍不要改样式更有效」。
  • 能在自己项目里找出至少一处「同一件事写在两个地方」。
CHAPTER 2

验收前置：从「看着还行」到「跑得过断言」

全书最值钱的一章。把「怎样算做对了」写成会跑的代码，这是从「派活」到「工程」的分水岭。

核心转变

旧流程：需求 → agent 干活 → 人眼看 → 提意见 → 再干。你的晨报 v1→v6 就是六轮这个循环，每一轮的「意见」其实都是一条本该提前写明的验收标准。

新流程：验收标准（代码） → agent 干活 → 机器判 → 不过就把错误原文回传重试 → 通过才允许发布。

关键不是「多一道检查」，是失败信息能直接被 agent 拿来改

三类断言

类型例子（你的项目）怎么测
结构断言15 个 <section>、15 条锐评、5 个说人话框、13 个名词正则 / DOM 计数
一致性断言报头期号 = 报尾期号 = issues.js 期号；site/ 与源文件 md5 相同；跨版星数一致跨文件比对
行为断言390px 视口 scrollWidth === clientWidth；点上一期能切到 001；线上 APK 返回 200 且 md5 一致CDP / curl / 脚本

断言要满足三个条件：可执行（不是写在规范里的一句话）、能定位（说清哪个文件、实测几个）、有明确退出码（下游据此决定发不发布）。

逐段读配套脚本 examples/validate.py

① 统一收集结果，失败信息可读

results = []
def check(group, name, ok, detail=""):
    results.append((group, name, bool(ok), detail))
    print(f"  [{'OK  ' if ok else 'FAIL'}] {name}  ·  {detail}")

def finish():
    bad = [r for r in results if not r[2]]
    if bad:
        print("未通过（把这些原文回传给 agent，让它自己改）：")
        for g, n, _, d in bad: print(f"  · [{g}] {n} {d}")
        return 1                 # 退出码 1 → 下游禁止发布
    return 0

注意 detail：写「实测 14」而不是「不通过」。agent 拿到「15 条锐评 实测 14」就知道去补一条，不需要人再翻译一遍。失败信息是给 agent 的输入，不是给人看的日志。

② 断言要精确，否则会误报

写「正文只用中文引号」这条时，我实测发现按字面写会报错：正文里有半角引号，但都在命令行示例代码里，属于合理例外；另外报尾「往期：第 001 期」会让「期号唯一」误判。所以脚本里做了两处精确化：

def body_text(html):
    # 排除 script / style / code / pre：命令行示例里的引号不算正文
    t = re.sub(r"<(script|style|code|pre)\b[^>]*>.*?</\1>", " ", html, flags=re.S | re.I)
    return re.sub(r"<[^>]+>", " ", t)

# 期号不要求「全文唯一」，只要求报头与报尾一致
title_no = issue_from(re.search(r"<title>(.*?)</title>", t, re.S).group(1))
colophon  = re.search(r'class="colophon"[^>]*>(.{0,400})', t, re.S)
check("A", "报头/报尾期号一致", title_no == issue_from(colophon.group(1)))
这是个重要的方法论副产品把含糊的规则写成代码时，你会被迫回答「命令行算不算正文」「往期引用算不算期号」。也就是说，写断言的过程本身就是澄清需求的过程。规范里那句「正文只用中文引号」从来没被定义清楚，直到要写成代码才暴露出来。

③ 把踩过的坑固定成断言，防复发

# 这次真实踩过：.btn 的 display 覆盖了 HTML 的 hidden 属性
check("C", "hidden 兜底仍在",
      re.search(r"\[hidden\]\s*\{[^}]*display\s*:\s*none", e) is not None)

这条断言的价值不在「检查 CSS」，在于以后任何人（或任何一次模型生成）把那行兜底删掉，CI 会立刻拦下。故障复盘的产出不该只是一句「以后注意」，应该是一条断言。

变异测试：证明断言不是摆设

配套脚本 examples/repair_loop.py 会在临时沙盒里复制一份可校验的最小项目，故意制造「11-05 少一条锐评 + 新一期还没同步进 site/」，再跑同一套断言：

  · [B] 2026-11-05 · 报纸已同步进 site/  site/ 缺 · 源 有

脚本抓到了，并且返回 1。注意一处退化引发两条失败，且修法不同：一条靠改 HTML 补锐评，一条只能靠跑 build_index.py 同步产物。所以工单必须列出全部失败项，不能只修第一条就宣布完成。没有做过变异测试的断言，你不知道它到底有没有在检查。以后每加一条断言，都故意破坏一次验证它会红。

失败闭环：怎么让 agent 自己改

for attempt in range(3):
    agent_do_task()
    r = run("python validate.py .")
    if r.returncode == 0: break
    agent_fix(prompt="自检未通过，原文如下，只修这些：\n" + r.stdout)
else:
    write_status("FAILED")   # 三次仍不过：留状态、停止发布、等人介入

三个要点：把原文回传（不要人转述）、限制只修失败项（避免它顺手改坏别处）、设重试上限并留下明确状态（防止无限循环和静默失败）。

现场跑过examples/repair_loop.py 把上面这段伪代码跑成了真的：python repair_loop.py 两轮收敛（29/31 → 32/32 → ALLOW）；--stubborn 故意漏跑同步，第 2、3 轮始终停在 30/31，触发熔断、写出 status.json 并保留现场；--gate <项目路径> 可对真实项目只判定不改文件。
写这个脚本时还抓到一个真实缺陷：validate.py 的「报纸已同步进 site/」原本没有 detail，工单里只剩一句「不通过」，agent 无从下手——现已补成「site/ 缺 · 源 有」。闭环脚本反过来会检验断言本身够不够格：失败信息不是日志，是给模型的输入。

  2. 加一条你自己的断言（例如「13 个名词速查」），故意破坏一次验证它会红。
  3. 把脚本接进出报流程：validate.py 退出码非 0 就不许执行重新发布。

  • 能说清「规范里写一条」和「代码里断言一条」的本质差别。
  • 能解释为什么失败信息要带实测数字、且原样回传给 agent。

CHAPTER 3

任务分解与可验证流水线

一个十二段提示词，不如五个能单独重跑的阶段。

为什么长链路会变脆

你现在出报是「检索 → 写作 → 排版 → 自洽检查 → 落盘 → 刷索引 → 发布」一口气完成。三个代价：

  • 错误定位成本高：最终发现头条素材不对，无法只重跑检索，只能整期重来。
  • 中间状态不可见：没有「素材 JSON」这个可检查物，事实核查只能混在写作里做。
  • 上下文压力：越到后面的步骤，模型离前面的约束越远，这正是「自洽硬检查」容易漏的原因。

分阶段模板

stage1_search    →  material.json      # 只检索，结构化落盘，可人工抽查
stage2_verify    →  material.checked.json  # 独立一步核对数字/日期/来源
stage3_write     →  body.md            # 只写正文，不碰 CSS
stage4_assemble  →  AI晨报-DATE.html   # 脚本拼装（模型不参与）
stage5_validate  →  validate.py        # 断言，退出码决定去留
stage6_publish   →  build_index.py + deploy

每一步满足三个条件才叫「阶段」：有明确输入输出、产物落盘、能单独重跑且不破坏下游。中间产物用结构化格式（JSON / Markdown 片段），不要自由文本——结构化才容易被断言检查。

可验证性设计

这是比「分解」更重要的一步：让每一步的产物天然容易检查。例如素材阶段要求每条带 source、date、number 字段，那么核查阶段就能机器比对「同一项目在不同版的星数是否一致」，而不是靠模型自己记。

和你晨报内容的一个呼应你在第 05 版拆过 harness 的思路：模型负责提议，外壳负责记账和校验——工具调用写进模型改不了的 Record，回合末用自述对账。流水线设计是同一个原则的放大版：别指望模型「记得自己说过什么」，把状态交给外壳存成文件，再由代码核对。

幂等：同一输入重跑，结果相同

你的 build_index.py 已经做对了：复制前先比文件大小，不重复覆盖；每次完整重写 issues.js。所以今天跑一次和跑三次，结果一样。这叫幂等，是自动化能安全重试的前提。

反例：如果脚本是「往索引里追加今天这一期」，重跑两次就会多出一条重复记录。写脚本时优先「全量重建」而不是「增量追加」，全量重建天然幂等。

动手练

  2. 设计一个 material.json 的最小 schema，让「跨版数字一致」可以机器比对。
  3. 挑出出报流程里最该独立成一步的环节，说明它为什么现在混在里面会出问题。

最小权限与授权边界

把动作分三档，写进 AGENTS.md 让 agent 自己遵守：

A 档（可自动）：读文件、跑只读命令、生成本地临时文件、跑 validate.py
B 档（做完要报备）：写项目内文件、重打 APK、生成桌面快捷方式
C 档（必须先问）：重新发布线上站点、改自动化提示词、动桌面上已有文件、任何删除
你已经在做的一件对的事「发布同意不跨轮」——每次改动已上线站点要重新发布，都在当轮先确认。这就是 C 档动作的正确处理方式，把它写进契约，别只留在我的工作日志里。

原子写：杜绝「半截文件被当成成功」

这是你补发检查里一个真实的漏洞：它用「文件是否存在」判断今天出报没有。如果 8 点那次生成到一半崩了，留下一个 15 版只写了 6 版的 HTML，补发检查会认为「已出报」直接跳过。修法是临时文件 + 校验 + 原子改名：

import os
from pathlib import Path

tmp = target.with_suffix(".html.tmp")
tmp.write_text(html, encoding="utf-8")
if validate(tmp) != 0:          # 先校验临时文件
    tmp.unlink(); raise SystemExit("校验未过，不落盘")
os.replace(tmp, target)         # 同一分区内改名是原子的
# 观察者在任何瞬间看到的，要么是旧文件，要么是完整新文件

配套地，判断「今天成没成」不要看文件存在，要看一个显式状态：

status.json = {"date":"2026-11-05", "state":"OK",
               "validated":32, "published":true, "at":"08:04"}

工具描述怎么写

给工具写说明时，写边界不写自由。反例：「可以执行任意命令」。正例：「只允许在 ai-daily/site/ 下写文件；不允许删除；发布前必须通过 validate.py」。工具描述本身是上下文的一部分，写得模糊等于放权。

原子写的完整实现（可运行）

examples/pipeline.py 里每个阶段都走同一个函数。它把「校验」做成参数传进来，校验不过就删临时文件、目标文件一个字节都不动：

def atomic_write(path, text, validator=None):
    tmp = path.with_name(path.name + ".tmp")
    tmp.write_text(text, encoding="utf-8")
    if validator:
        code, why = validator(tmp)          # 先校验临时文件
        if code != 0:
            tmp.unlink(missing_ok=True)
            raise RuntimeError(f"原子写被拦下：{why}（目标文件未被触碰）")
    os.replace(tmp, path)                   # 同分区改名是原子的
    return md5(path)

# assemble 阶段注入骨架校验：缺 style 或 viewport 就拒绝落盘
atomic_write("paper.html", html, validator=check_skeleton)

为什么是 os.replace 而不是「先删旧文件再写」：前者在文件系统层面是一步完成，任何时刻的观察者看到的要么是旧文件、要么是完整新文件；后者中间存在一个「文件不存在」或「写了一半」的窗口。你补发检查用「文件存在」判断成功，正好会踩进这个窗口。

把 A / B / C 三档写成代码，而不是写成口号

契约里写「C 档必须先问」只是文字；脚本里应该有一道真的过不去的检查：

PERMISSION = {
  "read":       "A",   # 读文件、跑只读命令、跑 validate.py
  "write_local":"B",   # 写项目内文件、重打 APK（做完报备）
  "deploy":     "C",   # 重新发布站点（当轮明确授权）
  "delete":     "C",
}
def guard(action, approved=False):
    level = PERMISSION[action]
    if level == "C" and not approved:
        raise PermissionError(f"{action} 属于 C 档：未获本轮授权，拒绝执行")
    return True

# 发布闸门：先校验，再授权，最后才动手
guard("deploy", approved=user_said_yes_this_turn)
if run("validate.py").returncode != 0:
    raise SystemExit("断言未过，禁止发布")     # 闸门在副作用之前

CHAPTER 5

自动化与可靠性

定时任务最危险的不是不跑，是「跑了但没成」却看起来成了。

定时任务的三个谎言

  1. 「跑过了」≠「成功了」：进程退出码、异常、超时都要检查。
  2. 「文件存在」≠「内容正确」：就是你补发检查现在的判断方式。
  3. 「没报错」≠「下游同步了」：出报成功但 build_index.py 或重新发布失败，桌面能看到、手机看不到，而且没人知道。

给你两条自动化逐条体检

现状风险改法
8:00 出报 → 刷索引 → 发布，串在一段提示词里任一步失败，后续可能仍被执行或静默跳过每步查退出码；失败即中止并写 status.json
补发检查：文件存在就跳过半截文件会被当成已出报改为读 status.json 的 state == OK，且跑一次 validate.py
补发检查每 3 小时跑一次正常日子重复判断、异常日子可能反复补发加「当天已尝试」标记，避免重复出报
没有失败通知连续几天没出报，要等你自己打开发现至少把失败写进产物；进阶是发一条消息

状态可查，是无人值守的最低要求

设计一个任何人（包括下次的 agent）一眼能看懂的状态文件，并且它是流程最后一步写的：

{
  "date": "2026-11-05",
  "state": "OK",              // OK | FAILED | PARTIAL
  "steps": {
    "generate": "OK", "validate": "OK:32/32",
    "index": "OK", "publish": "OK"
  },
  "error": null,
  "at": "2026-11-05 08:04:12"
}

注意 PARTIAL 这个状态很有用：出报和刷索引成了、发布没成，就该标 PARTIAL，允许下次只补发布，而不是整期重来。这就是补偿：知道断在哪，就能从哪继续。

重试、退避与熔断

  • 重试只针对瞬态失败（网络超时、下载源抽风），且同一动作要幂等。
  • 退避：连续失败别立刻死循环，间隔拉长。
  • 熔断：连续 N 次失败就停止并留状态，等人介入；不要让自动化无限重试一整夜。
一个真实对照这两天装 Android 工具链时，第一次下载脚本因为 sdkmanager.bat 在 Git Bash 下路径问题失败了；改成直接调 java -classpath ... SdkManagerCli 才成功。这类失败就该「换个执行方式重试」，而不是把整条链路从头跑一遍。分阶段的价值在这里也体现出来：JDK 和 SDK 已经解压好了，只重跑第 4 步即可。

现场演示：状态机的四种结局

examples/status.py 用四个场景把「文件存在 ≠ 成功」跑成了可观察的事实：

=== 场景 1 · 全绿 ===
  state=OK       steps=generate:OK validate:OK index:OK publish:OK
  should_skip(2026-11-05) = True   resume_from = None

=== 场景 2 · 发布失败 ===
  state=PARTIAL  steps=generate:OK validate:OK index:OK publish:FAILED
  resume_from = publish   → 只重跑 publish，前三步产物保留

=== 场景 3 · 半截文件 ===
  文件存在 = True（43 字节，只写了 6 版）
  state=FAILED   should_skip(2026-11-07) = False  → 补发检查会正确触发

=== 场景 4 · 连续失败 ===
  第 1/2 次：FAILED    第 3 次：FAILED  error=CIRCUIT_OPEN

场景 3 就是你补发检查现在最危险的地方：它只看 AI晨报-YYYY-MM-DD.html 在不在。换成 should_skip() 后，半截文件不会被当成「今天已出报」。

状态机的最小实现

STEPS = ["generate", "validate", "index", "publish"]

def mark(step, ok, detail=""):
    d["steps"][step] = ("OK:" + detail) if ok else ("FAILED:" + detail)
    save()                                  # 每步都落盘，崩溃也知道断在哪

def finish():
    vals = [d["steps"].get(s, "PENDING") for s in STEPS]
    if all(v.startswith("OK") for v in vals):      d["state"] = "OK"
    elif any(v.startswith("FAILED") for v in vals):
        d["state"] = "PARTIAL" if any(v.startswith("OK") for v in vals) else "FAILED"
    if d["state"] == "FAILED" and d["attempt"] >= 3:
        d["error"] = "CIRCUIT_OPEN：停止重试，等人介入"

def resume_from():                          # 补偿：从第一个没成功的步骤续跑
    return next((s for s in STEPS if not d["steps"].get(s,"").startswith("OK")), None)

def should_skip(date):                      # 只看状态，不看文件
    return d.get("date") == date and d.get("state") == "OK"
两个容易漏掉的顺序① 开工先写 RUNNING，收工才写 OK：如果一上来就写 OK，中途崩了反而留下「成功」的假状态；② 状态文件自己也要原子写（status.py 里用的 atomic_json 就是 os.replace），否则状态文件本身可能半截。判据自己不能被判据的故障骗过。

给你两条自动化的改造清单

把现在「一段提示词串到底」改成下面这个形状。注意每一步都有退出码检查、失败即中止、且 finally 里一定留状态：

# 8:00 每日出报

try:

    guard("deploy", approved=True_asked_this_turn)
    deploy(); book.mark("publish", True)
except Exception as e:
    book.mark(current_step, False, str(e)[:200])     # 失败原文，不转述
finally:
    book.finish()                           # OK / PARTIAL / FAILED 三选一

# 每 3 小时补发检查（先读状态，再决定做不做）
if StatusBook("status.json").should_skip(today):
    print("今日晨报已出且校验通过，无需补发"); return
if attempts_today >= 3:

这里有个和第 2 章闭环呼应的地方：GateBlocked(r.stdout) 把失败原文留下来，下一轮 agent 拿到的就是「15 条锐评 实测 14」这种能直接动手的信息，而不是人转述的「校验没过」。

PARTIAL 是省钱的状态出报成功、索引刷好、发布超时，标 PARTIAL 并记录 resume_from = publish。下次只需补一次发布，不用重新检索 12 路、重写 15 版。状态越细，补偿越便宜。

版本控制与可回滚

不需要学完整 git，六条命令就够把「改坏了」从灾难变成一句话。

最小可用集

# 每次让 agent 改之前：

# 改完发现不对：

git checkout -- site/index.html   # 单文件回滚
git reset --hard HEAD~1           # 整体回到上一版（慎用，先确认无未提交的重要产物）

三条纪律：改动前先提交（有快照才敢放手让 agent 改）、一次交付一个 commit（信息明确）、提交信息写「做了什么」而不是「update」。

CHAPTER 8

把 agent 做进产品

前七章是「agent 帮我开发」，这一章是「产品里带一个 agent」。门槛最高，也最能拉开差距。

先判断该不该用

确定性任务用代码，不要用 agent。「温度超过 85℃ 就标红」是 if 语句；「温度突然升高，结合当前进程、驱动版本、近期改动，判断可能原因并给出建议」才需要 agent。判断标准很简单：如果输出无法用规则枚举，且需要跨来源关联，才值得请模型。

最小 function calling 循环

tools = {
  "read_sensors": lambda: collector.latest(),
  "list_processes": lambda: ps.top_by_gpu(),
  "read_log": lambda path, n: tail(path, n),
  "write_diagnosis": lambda text: db.insert(text)   # 唯一有副作用的工具
}
while True:
    act = model.decide(context, tools_schema)
    if act.name == "finish": break
    if act.name not in SAFE_TOOLS and not user_approved(act): continue
    result = tools[act.name](**act.args)
    context.append({"tool": act.name, "result": result})  # 留 trace
    if token_cost(context) > BUDGET: break               # 成本上限

四个不可或缺的东西：工具白名单、副作用单独授权、每步 trace 可观测、成本与步数上限。少了任何一个，demo 能跑，长期会出事。

两个可在你项目里落地的方案

方案 A：监测器的异常诊断 agent

现在的 MonitorWidget + server.py / collector.py 是「采集 → 展示」。加一层：温度/占用率异常触发时，agent 拿着只读工具去查当前进程、GPU 占用、最近几分钟曲线，产出一句带依据的诊断（而不是一句「温度偏高」）。只给只读工具，不让它改设置；诊断写进日志，由用户决定是否采纳。

方案 B：晨报的事实核查 agent

把「核对数字、日期、跨版一致性」从写作里拆出来，变成一个独立阶段（第 3 章）：输入 material.json，输出 checked.json + 冲突清单。它甚至可以不参与写作，只做校验——这是最容易落地、风险最低的产品化 agent，因为它只有否决权，没有发布权。

最常见的翻车点把 agent 直接接到「能改数据 / 能发消息」的工具上，又没留 trace。出问题时你既不知道它为什么这么做，也无法回滚。正确顺序永远是：只读 → 可观测 → 有 dry-run → 最后才给写权限。

现场演示：四个机制，四种结局

examples/agent_loop.py 用确定性规则模拟 model.decide()，不调用真实模型也能把四种情况跑通：

=== 正常：只读三件 + 授权写入 ===
  调用：['read_sensors','list_processes','read_log','write_diagnosis']
  花费：480 tokens / 步数 4    落库诊断：1 条

=== 未授权：只给只读工具 ===
  调用：['read_sensors','list_processes','read_log']
  拦截：副作用工具未授权：只读完成，不写入    落库诊断：0 条

=== 成本上限（200）===
  调用：['read_sensors']
  拦截：成本上限：120 + 120 > 200

  调用：['read_sensors','list_processes']
  拦截：白名单拦下未知工具 delete_logs

最后一个用例最关键：模型「想」调一个不存在的工具时，外壳直接拒掉，而不是把错误抛给下游或让它换个名字再试。白名单不是文档里的一句话，是循环里的一行 if name not in TOOLS。

工具契约：把边界写成 schema，而不是写在提示词里

{
  "read_sensors":  { "side_effect": false, "args": {},
                     "desc": "只读：返回 CPU/GPU 温度、占用率、风扇转速" },
  "list_processes":{ "side_effect": false, "args": {},
                     "desc": "只读：按 GPU 占用排序列出进程" },
  "read_log":      { "side_effect": false, "args": {"n": "1-20"},
                     "desc": "只读：最近 n 条系统日志" },
  "write_diagnosis":{ "side_effect": true, "needs_approval": true,
                     "desc": "唯一写操作：把一句带依据的诊断记入日志" }
}

每个工具都写清 side_effect 和参数范围。这段 schema 本身就是喂给模型的上下文——写得含糊等于放权；写成结构化字段，外壳就能在调用前机械判断该不该拦。

trace 该记什么，以及四级放行顺序

字段为什么必须有
step / tool / args复盘「它为什么这么做」，而不是只看最终结果
result区分「模型说错了」和「工具返回错了」
cost / 累计 spent成本上限才有依据，不是拍脑袋
event：TOOL / BLOCKED被拦也要留痕，否则你以为它没尝试过

放行顺序永远不能跳：只读 → 可观测 → dry-run → 才给写权限（且配回滚）。方案 B「晨报事实核查 agent」之所以是最低风险的起点，是因为它只有否决权、没有发布权：输出一份冲突清单，由人决定是否采纳，连写权限都不用给。

方案 A 怎么评价它说得对不对监测器诊断 agent 的输出不能只写「温度偏高」，必须引用 trace 里的具体读数（如「GPU 97%、blender.exe 占 71%、驱动 26.9.1」）。评估方式：把诊断里的每个数字回查 read_sensors / list_processes 的返回值，对不上就判失败。这样第 2 章的断言就能复用在自然语言输出上——让「有依据」变成可机器核对的事。

交付前自检清单

每次让 agent 交付前，花两分钟过一遍。前期靠自觉，后期应该全部变成脚本。

  • 路径写死在 AGENTS.md，且本次产物落在唯一真源位置。
  • 本次任务的验收标准，至少有一条是可执行断言（不是文档里的话）。
  • 新加的断言做过变异测试，确认它会红。
  • validate.py 退出码为 0，失败原文没有被人工「翻译」过。
  • 所有写操作之前有 commit 或备份，能一句话回滚。
  • 落盘用临时文件 + 校验 + 原子改名，没有半截产物。
  • 「成功」由 status.json 的 state 判定，不是由文件存在判定。
  • 多步流程每一步都有退出码检查，失败会中止并留状态。
  • 涉及线上的动作有明确授权，且发布闸门在校验之后。
  • 跨文件一致性（期号、日期、数字、md5）已被机器比对过。
  • 行为验证用的是可信手段（真实视口 / 实际请求），不是看起来像。
  • 踩过的坑已固化成回归断言，不靠「以后注意」。
  • 脚本重跑一次结果相同（幂等），没有重复记录。
  • 失败时有明确状态或告警，不会静默。
  • 交付说明里写清了「哪些没验证」，不把未知说成通过。

边界越权提前发布明天的报、提案没被点名就自行实施L0 红线 + 默认行为写死

分类不是为写报告，是为了问一句：同一类故障是不是由同一道闸门在管？如果两次「漂移」靠两个不同的补丁挡着，说明还没找到机制层。

F.3 假绿：今天最贵的一课

外部评审一句话戳中要害：特刊是 16 版，读者翻到第 15 版，页眉写着「共 15 版」，而自检盖的是全绿章。拆开来是三种形态，每一种单看都很「合理」。

① 抽样当全量

断言 A4b 检查了 <title>、报头、报尾三处的版数，三处都对；可页眉有 14 处，一处都没查。make_manifest.py 的 pages_in_title 更省事，只从标题取一个数。修法不是「再加一处抽查」，是把检查对象从「代表样本」换成「全部实例」：

claims = re.findall(r"共\s*(\d+)\s*版", full)      # 全文，不是前三处
if len(claims) != pages or any(int(x) != pages for x in claims):
    errs.append("A4d 全文 %d 处版数写法与实际 %d 版不符" % (len(claims), pages))

# 页眉还要单独对账：条数 = 版数 - 1，页码 p02..p16 连续
headers = re.findall(r"第\s*(\d+)\s*版\s*/\s*共\s*(\d+)\s*版", full)
assert len(headers) == pages - 1 and all(int(m) == pages for _, m in headers)

② 三态里的 None 被放行

凭证里用 True / False / None 三态，None 表示「本期没这个版式，不参与判定」。但汇总写成了：

ok = all(v is not False for v in checks.values())   # None 也算过

# 正确做法：先分清「必查项」和「可选项」
REQUIRED = ("pages_eq_nav", "nav_matches_sections",
            "sections_continuous", "pages_all_match")
ok = (all(checks[k] is True for k in REQUIRED)          # 必查项取不到就判 False
      and all(v is not False for v in checks.values())) # 可选项只不许 False

「取不到值」和「检查通过」是两件事。把前者当成后者，等于给检查器留了一个静默的后门。

③ 只验可达，不验内容

线上检查原来只请求到 HTTP 200 就算过。改完本地文件没发布，200 照样有——于是又出现「本地是新版、线上是旧版、自检全绿」。修法是比对内容摘要：把本地成品的 sha256 与线上响应体算出来的 sha256 对齐，不一致就红。

一句话定理检查器只能证明它检查过的东西。绿章的可信度等于覆盖面的下界，不等于通过项的数量。所以「自检从 8 项加到 10 项」本身不提升安全性——新增的两项如果仍是抽样，错的东西照样在覆盖之外。

F.4 五层闸门：缺一层就漏一类

层今天的实例拦什么为什么不能并到别层
L0 红线（契约）R06 自检有 FAIL 不许说完成；R07 报纸日期必须是出报当天人和 agent 的行为代码拦不住「嘴上说已完成」
落盘前断言A4b/A4c/A4d 版数与期号、A9 系列术语一致生成物本身错落盘后再查，读者已经能看到
交付前自检selfcheck.py：索引、凭证、期序、日期、全文版数跨文件一致性单个生成器看不到别的文件
发布后线上验证curl 五处 200 + sha 比对 + 手机视口 CDP部署漏文件、缓存给旧版本地全绿推不出线上对
状态机与凭证status.json 五阶段、每期同名 json「谁在什么时候验过」没记录就无法判断明天该不该重跑

每一层都要能独立说红，而且红的时候给出「哪里 / 期望什么 / 实际什么」，不能只给一个退出码。

最容易被跳过的是第五层撤下 11-07 未来期时，除了移走文件、删站点副本、重建索引，还必须把 status.json 回滚到 11-06/003。否则次日的启动检查读到「11-07 已完成」，会判定 ok 而静默——明天的报就没人做了。状态不是日志，是下一轮决策的输入。

F.5 反向验证：修完还得证明闸门会红

「跑一遍全绿」只证明现在没坏；「故意弄坏看它红」才证明检查器在工作。今天在真实项目里做了五次：

故意弄坏期望谁红
移走一份 json自检「每期都有 manifest」红
往 p07.html 塞回「共 15 版」拼版断言 A4d 红，产物不许落盘
AI_DAILY_TODAY=2026-11-05 假装是昨天日期闸门红（今天这份成了「未来期」）
临时目录里放一份 11-07 的报纸build_index.py 跳过并告警，不同步
本地改了文案但不发布线上 sha 比对红——这次它真的红了，说明改动没同步

这就是第 7 章的变异测试。没做过反向验证的自检项，只能算「写过」，不能算「有用」。

把一次性验证固化成命令当天这五次全是手工命令，跑完就没了——教案教了，生产项目却没留下入口。后来补了 python ai-daily/tools/mutation_test.py：在临时目录里给每个检查项造一个反例（错版数、缺凭证、等长漂移、未来期……），要求对应检查项变红，反例不碰任何成品。以后每加一条自检项，就在这里补一个变异，否则新项只是「写过」。
最初有两项被如实标成 SKIP：术语缺词表缺 HTML fixture、线上 sha 要「改了没发布」不便制造事故。后来都用隔离替身补齐——复制一份真实特刊、把报尾词表整批改错字；起一个 127.0.0.1 随机端口的假站点，只对本地副本做等长替换。不能制造的事故，就造一个隔离的替身，不要因此把检查项留在「没测」里。
每个反例还必须先跑一次正向对照：底板全绿了，弄坏后的红才算数——否则服务没起来也会「变红」，那是假红，比假绿更骗人。跑完报告里 SKIP 也要写出来：没测就是没测。

F.6 漂移治理：让事实只有一份

  • 单向同步 + 独立对账：根目录成品 → site/，按内容比对，内容不变就不写（保住 mtime，manifest 才幂等）。但「同步跑没跑过」不能靠约定保证：自检再把源与副本逐字节比一次。只比 size 会漏掉等长替换——改一个词、改一处版数，字节数一模一样，两份真相从此分叉却无人报警。
  • 凭证对账：每份成品有同名 json，记 path / sha256 / bytes / terms / glossary / checks / ok；自检第 4 项拿它跟实际文件逐个对。
  • 数字不手写第二遍：文档里「自检 8 项 → 10 → 11 → 12」来回改了四轮。最后给脚本加 --list，三份文档统一改成「项数以 --list 为准」，不再写数字；AGENTS.md 里那张手抄的验收表也整个删掉（它一度停在 10 项，脚本已经 12 项），名称和排障提示都由 --list 输出。
  • 教材自己也是这套：增补片段放在 expand_tutorial.py 的 EXTRA 里，靠 <!-- extra:ID --> 标记幂等替换；练习题只在教材写一份，build_qa_index.py 自动派生到《教程问答.md》。

凡是「同一个事实需要在两处手写」的地方，迟早会漂。能派生就别抄，能比对就别记。

F.7 把判断写成规则，而不是靠记得

日期闸门 R07：查四处，不是查一处

「不许提前发明天的报」听起来是常识，落地要查：根目录成品、site/ 副本、issues.js 索引、status.json 状态机。少查一处，就会从那一处漏回读者面前。构建索引时还要主动跳过未来期并告警。

沉默即否决：把默认行为写死

第 16 版每期提四条建议，只有用户明确说「采纳 P004-2」才动工；没说就是否决，不自行实施、也不追问。规则的价值在于把「要不要做」从 agent 的临场判断里拿走。

发布 ≠ 可见：检查「能不能走到」，不是「文件在不在」

特刊当时确实发布成功了，但 issues.js 没有它、入口页没有它，两端都打不开。补齐首屏横幅、往期书架、深链 ?d=&s=1 三处才算完成；还要考虑 HTTP 启发式缓存与 Service Worker。

同一天两期：先定排序语义，再写页面

特刊不是单独的书架区，而是当天的第 2 版 003-2，排序键 (date, issue) 倒序。还有一个反直觉的决定：默认落当天正刊，不是「最新一期」——否则横幅形同废码。默认行为要跟着产品意图走，不能图省事。

F.8 评审也要验收；编辑决策别替用户做

那份外部评审列了 7 条，逐条核对的结果是：5 条成立、2 条只对一半、3 处细节说错。不核对就照单全收，会白改甚至改坏。

评审原话核对结果
「全项目无来源声明」不成立：每期报尾都有「信息源 / 编辑说明 / 本报由 AI 自动编撰」，缺的是项目级演示声明，不是来源
「双份真相是 11-06 两版互覆盖的根源」归因错：那次是拼版脚本同名覆盖，已有退出码 3 的闸门；单向复制反而是能自愈的
「7 次新提交」数字错：当天实际 17 次

最后那轮「只去内部话术」最能说明边界：搜全项目后发现同类话术在 4 个文件里（含已发布的 002 期），但「官方补发 Q4 量化脚本」是新闻正文，长得像却不能替换；「要不要加一行本报告为演示」是编辑决定，用户没选就不做。先分清楚哪些是工程问题、哪些是内容决定，再动手。

四个会骗人的工程细节① Windows 上 Path.write_text() 会把 LF 写成 CRLF，git diff 整文件炸开——用 bytes 级替换并校验每处只命中一次；② msedge --headless --screenshot 是桌面模式，会把 390px 顶栏误报成溢出，布局结论只认 CDP mobile:true；③ 线上中文路径要 percent-encode，还要先访问入口换到 cookie，否则 200 都拿不到；④ 后台进程不能用 shell & 起，会被回收。

F.10 三张可以抄走的清单

【改一处文案之后】
搜全项目 → 分清「运营话术 / 正文内容」→ 改所有源（含备选版本）
→ 重跑单向同步 → 重生成凭证 → --pre → 发布 → --online + 线上抽检
→ 记 deploy/verify → git commit

【收到一份评审之后】
逐条核对（成立 / 部分成立 / 不成立，附证据）→ 只修成立的部分
→ 把根因固化成闸门 → 故意弄坏一次看它会不会红 → 再发布 → 复验

【说「已完成」之前】
--pre 全绿 → --online 全绿 → 没有「本地改了没发布」的漂移
→ 状态机五阶段齐 → 有一个可回滚的 commit → 未验证项如实列出
动手练
  1. 在 learn-agent/demo/ 里把 validate.py 的一条断言改成「只检查第一张卡片」，跑 verify.py 看它是否仍然全绿；再改回全量，用一句话说明抽样为什么危险。
  2. 在 ai-daily/tools/make_manifest.py 里找出一处三态 None，判断它属于「必查项」还是「可选项」；把必查项取不到值的情况改成判 False，并故意让它取不到，确认 ok 变红。
  3. 用 AI_DAILY_TODAY 分别模拟「昨天」和「明天」，写出日期闸门在两种情况下各应给什么结论，说明为什么状态机也必须一起查。
  4. 从 R07（日期）、沉默即否决、发布≠可见里挑一条，写成一道能自动判定的断言，并指出它该放在 F.4 五层中的哪一层、为什么。
  5. 挑一段已发布的正文，列出「改它之前要搜哪些位置、哪些字符串不能一起替换」，写成一份替换清单，再说明哪一步属于编辑决策、不该由你替用户定。
带走的三个判断① 绿章不等于对——先问检查器覆盖了什么；② 改完不等于完成——源、副本、凭证、索引、状态、线上、提交七处对齐；③ 修完不等于会防复发——故意弄坏一次，看它会不会红。这三条比今天新增的任何一个脚本都值钱。
