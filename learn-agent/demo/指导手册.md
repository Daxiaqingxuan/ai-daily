# 实例项目 · 晨读卡：从零跑通一条闭环

> 这是一份**带着你动手**的示范。七步，每步都回答三件事：
> **做什么（命令）· 为什么这么做（原理）· 怎么算做对了（验收）**。
>
> 项目位置：`learn-agent/demo/`，与 `ai-daily/` **完全独立**——不共享路径、不引用文件、不被自动化调用。
> 在这里练坏了只影响这里，晨报照常出。
>
> 预计时间：跟着敲 30–40 分钟；只读不敲 10 分钟。

---

## 第 0 步 · 先看全貌：为什么另起一个项目

**做什么**

```bash
cd learn-agent/demo
find . -type f -not -path "./site/*" -not -path "./stages/*" | sort
```

你会看到 9 个文件：1 份契约、1 份素材、2 个模板、4 个脚本（另加本手册）。

**为什么**

你真正想练的是「怎么让 agent 的产出可验收、可回滚、可复现」，而这件事在晨报上练有三重风险：

1. 晨报每天 8 点自动跑，改坏了第二天就没有报纸；
2. 一期 15 版、144KB、6 端产物，一次改动牵扯太多；
3. 真出问题，你分不清是「方法不对」还是「这一期素材不好」。

所以这里造了一个**结构同构、规模 1/20** 的项目：

| 晨报 | 晨读卡 | 迁移时改什么 |
|---|---|---|
| 15 个版面的报纸 | 1 张卡片 | 模板与 CSS |
| 12 路检索 + 15 版正文 | 1 条本地素材 | 素材来源换成检索结果 |
| `issues.js` 往期索引 | `index.json` + 卡片墙 | 索引字段 |
| `validate.py` 32 条断言 | `validate.py` 20 条 | 断言内容 |
| `status.json` 状态机 | `status.json` 状态机 | **不用改** |
| 发布到公网 | **不发布**（故意留白） | 加一步部署 |

**怎么算做对了**

你能说出「这个项目里哪一部分和晨报是同一套方法，哪一部分是业务细节」。说不出来就往下看，七步走完自然就清楚了。

## 第 1 步 · 立契约：把约定从脑子搬进文件

**做什么**

打开 `AGENTS.md`，只读第 2 节「唯一真源」和第 5 节「不变量」。然后跑：

```bash
python tools/validate.py
```

首跑的输出里 A 组应该是 **3/3 通过**——注意，这时你一张卡都还没生成，契约却已经能被打分了。

**为什么**

agent 是**无状态**的：新开一个会话，它不知道你上次说过「报纸保存到 ai-daily/」。你唯一能指望的，是它打开会话时读到的那几个文件。

你的晨报踩过这个坑：主自动化原来把报纸存到自己的工作目录，桌面和手机都读不到。根因不是模型笨，是「报纸存哪」这句话散在三个地方，没有唯一真源。

所以契约要写死的不是「愿景」，而是**四件可核对的事**：

| 写什么 | 为什么必须写 |
|---|---|
| 唯一真源表（谁写、谁读） | 同一件事只允许有一个位置 |
| 目录结构 | 新会话第一眼就知道东西在哪 |
| 常用命令 | 不用每次重新摸索入口 |
| 不变量 + 权限档 | 「不许做什么」比「要做什么」更容易被违反 |

**怎么算做对了**

- `validate.py` 的 A 组 3/3，其中一条是「与晨报互不干扰」——它真的会扫全目录，出现 `ai-daily/` 路径引用就红。
- 你能回答：如果把「卡片墙模板路径」改到别处，需要同时改几个文件？答案应该是**一个**（`AGENTS.md` 表格 + 引用它的代码）。

**坑（我写这一节时真踩了）**

第一版检查器写的是「文件里出现 `ai-daily` 这个词就报错」，结果 `AGENTS.md` 里「**不**读写 `ai-daily/`」这句合法声明被误判。改成只认**路径式引用**（`ai-daily/` 或 `ai-daily\`）才对。

> 教训：约束要检查「行为」，不要检查「字眼」。

## 第 2 步 · 先写断言，再写生成器

**做什么**

此时 `site/` 还不存在。先看它红成什么样：

```bash
python tools/validate.py; echo "退出码=$?"
```

实测输出（节选）：

```
[A] 契约   3/3
[B] 素材   7/7
[C] 产物   1/7
   · index.json 可解析 —— 实测：缺 index.json 或无法解析（FileNotFoundError）
   · 卡片墙存在 —— 实测：site/index.html 缺
   · 索引与卡片数量一致 —— 实测：index.json 不可用，无法判定
[D] 防回归  3/3

结果：14 / 20 通过
退出码=1
```

然后才去写生成器（第 3 步）。顺序是**故意反的**。

**为什么**

正常人的顺序是「先做出来，再看对不对」。这个顺序在一次性交付时能用，因为你在场、你眼睛就是验收器。一旦每天自动跑、人不在回路里，它就失效了——你不知道「对不对」，只知道「有没有」。

先写断言会逼你回答一个平时含糊的问题：**怎样算做对了？** 这个项目里是 20 条，分四组：

| 组 | 问什么 | 例子 |
|---|---|---|
| A 契约 | 约定还在吗 | AGENTS.md 存在、无跨项目引用 |
| B 素材 | 输入合法吗 | 字段齐全、日期唯一、正文 1–60 字 |
| C 产物 | 输出对吗 | 索引与卡片一一对应、按日期倒序、转义正确 |
| D 防回归 | 以前修过的坑会复发吗 | 模板主色还在、产物无 `{{}}` 残留 |

**怎么算做对了**

- 首跑必须是**红的**，且失败项读起来像一句能动手的话。
- 你能分清「14/20 通过」里那 6 条为什么红——它们全是「产物还不存在」，不是「代码写错了」。

**坑**

断言写得太严会**误杀正确产物**。我第一版要求「卡片 HTML 里必须出现 `2026-11-06`」，但卡片按设计显示的是「11 月 6 日」，于是闸门把一张完全正确的卡拦下了。

> 原则：**第一条断言失败时，先怀疑断言，再怀疑产物。** 断言是代码，代码会有 bug。

## 第 3 步 · 把「一口气生成」拆成五个阶段

**做什么**

```bash
python tools/build.py --date 2026-11-06
```

实测输出：

```
=== 晨读卡流水线 · 2026-11-06 ===
  [select  ] 选中 q001（10 条素材中唯一匹配）        md5=25221939ef
  [render  ] 单卡已渲染 2.0 KB                      md5=1b2dd6d5ca
  [index   ] 索引 1 张（全量重建）                    md5=fb364d9a99
  [precheck] 断言 20/20 通过（针对待发布目录）
  [publish ] 写入 site/：3 个文件                    md5=fb364d9a99
```

再看中间产物：

```bash
ls stages/
# selected.json  card.html  index.json  precheck.ok
```

**为什么**

五个阶段不是随便切的，每个边界都满足三条判据（教材第 3 章）：

1. **产物能被断言检查**：`selected.json` 是结构化 JSON，不是一段自由文本；
2. **失败不污染上游**：render 崩了，`selected.json` 还在，不用重新选素材；
3. **重跑不破坏下游**：单独重跑 render，index 会全量重建，不会重复追加。

对应到你的晨报，就是「检索 → 核查 → 写作 → 拼装 → 校验 → 发布」。现在这六件事挤在一个 12 段提示词里，任何一环歪了都要整期重来。

还有两个刻意的设计：

- **precheck 检查的是「待发布目录」**（`stages/preview/`），不是已经上线的 `site/`。这样断言跑在**副作用之前**，不通过时 `site/` 一个字节都没动。
- **索引全量重建**：每次从磁盘上的卡片重新算，不做增量。天然幂等，重跑不会重复，也不怕中间崩过。

**怎么算做对了**

- `stages/` 里四份产物都在，且都能打开看。
- 故意清空现场再续跑，会得到一句人话：

```bash
rm -rf stages
python tools/build.py --date 2026-11-06 --from index
# 已拦下：从 index 续跑要求前序产物存在，缺：selected.json
#   → 先跑一次完整流水线，再用 --from 只重跑后半段。
```

**坑**

第一版没有 `REQUIRED` 表，`--from write` 在空沙盒直接抛 `FileNotFoundError`，看不出该先跑哪步。

> 教训：**阶段之间的依赖也要写成代码**，别指望调用方记得。

## 第 4 步 · 让输出可复现：日期、排期与幂等

**做什么**

```bash
python tools/build.py --date 2026-11-06 --twice
```

实测：

```
  [publish ] 写入 site/：0 个文件              md5=3563717a06
             （内容与线上一致，没有产生写入 —— 幂等的可见形式）
  card.html        1b2dd6d5ca vs 1b2dd6d5ca  一致
  index.json       3563717a06 vs 3563717a06  一致
  precheck.ok      f7cd5bf0b3 vs f7cd5bf0b3  一致
  selected.json    25221939ef vs 25221939ef  一致
结论：完全一致 → 幂等
```

**为什么**

幂等最容易被忽略的敌人是**时间戳**。索引里有一个 `updated` 字段，如果取 `datetime.now()`，同一份输入连跑两次必然得到两个不同字节，幂等永远测不过——而且你会以为是别的地方有问题，查半天。

这个项目的写法是：`updated = "<date> 08:00"`，取**排期时间**而不是当前时刻。真实项目如果必须写当前时间，幂等比对就要先规范化掉这个字段。

第二个细节：幂等不只是「结果一样」，还包括**不该产生写入**。publish 阶段会逐文件比对内容，一样就跳过；所以第二次跑你会看到「写入 0 个文件」。这比「重新写了一遍但内容相同」更有说服力——前者连修改时间都没变。

**怎么算做对了**

- 四份中间产物 md5 全部一致，结论行写「完全一致 → 幂等」。
- 第二次 publish 写入 0 个文件。

**坑**

把「跑得通」当成「幂等」是常见错觉。判断标准只有一个：**同一输入跑两次，字节是否相同**。

## 第 5 步 · 两个不可逆的小事：原子写与转义

**做什么**

先看原子写的实现（`tools/build.py` 里的 `atomic_write`）：

```python
tmp = path.with_name(path.name + ".tmp")
tmp.write_text(text, encoding="utf-8")
os.replace(tmp, path)          # 同分区改名，一步完成
```

再出 11-10 那张卡，看转义：

```bash
python tools/build.py --date 2026-11-10
grep -o "&lt;可复现&gt;\|&amp;\|<可复现>" site/cards/2026-11-10.html
# &amp;        ← 1 次
# &lt;可复现&gt;  ← 1 次
```

**为什么**

**原子写**解决的是「半截文件」窗口。如果先删旧文件再写新的，中间存在一个瞬间：文件不存在或只写了一半。你的补发检查恰好用「文件在不在」判断今天出没出报——正好会踩进这个窗口，把半截文件当成成功。

**转义**解决的是「文本被当成代码」。素材里那句 `先让它跑通…<可复现> & 「可验证」…`，如果不转义：

- `<可复现>` 会被浏览器当成一个未知标签，**直接吞掉不显示**；
- `&` 后面如果跟着字母，可能被解析成实体。

页面上就少字了，而且你不会发现——因为看起来「只是排版有点怪」。

**怎么算做对了**

- `grep` 只找到实体，没有裸标签。
- `validate.py` 里「正文已 HTML 转义」这条是**对每一张含特殊字符的卡**比对素材原文，而不是抽查某一天。
- 产物里没有 `{{` 残留（模板占位符必须全部被替换）。

**坑**

转义最容易漏的是**次要字段**：正文转义了，`tags` 和 `title` 忘了。这个项目里 `tags`、`title`、`source`、`author` 全部走 `html.escape`，索引里的 `title` 也转义。

> 判断方法：凡是「外部输入 + 会被插进 HTML」的组合，都要过一遍转义，不看字段重不重要。

## 第 6 步 · 状态机与闸门：失败之后怎么办

**做什么**

先看正常放行：

```bash
python tools/gate.py --date 2026-11-08
# 闸门判定：ALLOW → 已发布 · state=OK
```

再故意弄坏一次：

```bash
python tools/gate.py --date 2026-11-09 --break
```

实测输出（节选）：

```
  [index   ] 索引 5 张（全量重建）                md5=4c8447a58c
  [破坏    ] 已注入 2 处退化（模拟 agent 生成坏了）

闸门判定：BLOCK → 禁止发布，site/ 未改动
工单（原样发给 agent）：
{
  "date": "2026-11-09",
  "state": "FAILED",
  "failed_count": 2,
  "failed": [
    { "check": "索引与卡片数量一致", "detail": "索引 4 条 · 磁盘 5 张" },
    { "check": "卡片结构完整", "detail": "2026-11-09 缺 <blockquote>" }
  ],
  "instruction": "只修下列失败项，不要动其它文件；修完重跑 gate.py。"
}

状态已写入 status.json：state=FAILED · resume_from=index
```

然后续跑：

```bash
python tools/gate.py --date 2026-11-09 --resume
# 第 2 次尝试 · 从 index 开始
# → 索引 5 张 → 断言 20/20 → 发布 → state=OK
```

**为什么**

失败之后有三件事必须做对，缺一件就会变成「静默故障」：

1. **留状态**：`status.json` 记每一步 OK/FAILED、第几次尝试、补偿点在哪。不写状态，你只能靠回忆。
2. **给工单**：失败原文带实测值（「索引 4 条 · 磁盘 5 张」），agent 拿到就能动手；写「校验不通过」，它还得先猜。
3. **补偿点要指对地方**：我第一版把断点设成 `precheck`，结果续跑还是红——因为 `precheck` 只负责**判定**，不负责**修复**。正确的补偿点是 `index`：重新生成产物，再判定。

这就是为什么 `--resume` 的输出是「从 index 开始」，而不是「从 precheck 开始」。**补偿点必须指向「能重新生成产物」的那一步。**

**怎么算做对了**

- `--break` 后：`site/` 没变（可以比对时间戳或 md5）、工单两条都具体、`status.json` 里 `state=FAILED` 且 `resume_from=index`。
- `--resume` 后：只跑了 index/precheck/publish 三步，`attempt=2`，`state=OK`。

**坑**

`gate.py` 开工时会调 `begin(date)` 重置当天状态。第一版把「读断点」写在了 `begin` 之后，读到的永远是 `None`，续跑静默退化成「从头跑一遍」——看起来成功，其实把补偿机制废了。

> 教训：**状态的读写顺序本身就是逻辑**，不是无关紧要的实现细节。

## 第 7 步 · 一条命令回归，一次快照回滚

**做什么**

回归：

```bash
python tools/verify.py
```

实测：

```
[PASS] contract     契约有效 · 零 ai-daily 路径引用
[PASS] assertions   20/20 通过
[PASS] idempotence  连跑两次，4 份中间产物 md5 一致
[PASS] mutation     破坏 2026-11-06.html 后断言返回 1（会红）
[PASS] escape       尖括号与 & 均为实体
[SKIP] browser      加 --browser 启用（需本机 Edge，本次未跑）

--- 结论：PASS 5 / FAIL 0 / SKIP 1 ---
```

回滚演练（**在临时目录做，不要在教程目录里 `git init`**）：

```bash
TMP=$(mktemp -d) && cp -r learn-agent/demo/* "$TMP"/ && cd "$TMP"
git init -q && git add -A && git commit -qm "基线：能出 5 张卡"
printf '\n<!-- 被 agent 改坏了 -->\n' >> site/index.html
git diff --stat                      # 看清楚改了哪个文件、几行
git checkout -- site/index.html      # 一句话回滚
grep -c "被 agent 改坏" site/index.html   # 0
```

**为什么**

**变异测试**是回归里最容易被跳过、也最重要的一步：`verify.py` 会把项目复制到临时目录，故意删掉一张卡的 `<blockquote>`，然后要求 `validate.py` 返回 1。如果它仍然通过，说明那条断言根本没在检查——你一直在看一份假绿报告。

**SKIP 不计入通过**。浏览器渲染这次没跑，报告就如实写 `SKIP 1`，并给出启用方式。把「没测」写成「通过」是评估里最常见的自欺。

**为什么不在 demo 里 `git init`**：以后你要给整个工作区建仓库，嵌套的 `.git` 会让 `git add` 报 submodule 警告、内容被跳过。练 git 用临时目录，效果一样，不留隐患。

**怎么算做对了**

- `verify.py` 退出码 0，且报告里明确列出 SKIP。
- 故意删一条断言保护的 `[hidden]` 类的东西，`verify.py` 会红。
- `git checkout` 后文件回到基线，`git diff` 为空。

## 迁移回晨报：七条清单

按顺序做，每条都能单独验证：

| # | 动作 | 验收 |
|---|---|---|
| 1 | 把 `demo/AGENTS.md` 拷进 `ai-daily/`，按实际路径改表 | `check_contract.py` C1–C3 变绿 |
| 2 | 让 `build_index.py` / `build_apk.py` 从契约读路径，删掉硬编码 | C5 漂移消失 |
| 3 | `validate.py` 接进自动化：不过就不发布 | 故意删一条锐评 → 退出 1 → 不发布 |
| 4 | 自动化每一步写 `status.json`，含 attempt 与 resume_from | 断网一次，看它标 PARTIAL 而不是「成功」 |
| 5 | 补发检查改看 `state`，不看文件是否存在 | 造一个半截文件，补发仍会触发 |
| 6 | `git init` 打基线，之后每次交付一个 commit | `git diff` 能定位上次改了什么 |
| 7 | 把临时验证串成 `verify_all.py --online` | 一条命令出 PASS/FAIL/SKIP |

## 自检：五个问题

1. 为什么断言要写在生成器之前？—— 因为它逼你先定义「对」。
2. 为什么 `updated` 不能取 `now()`？—— 否则同一输入两次运行字节不同，幂等永远测不过。
3. 为什么 precheck 检查的是待发布目录？—— 闸门必须在副作用之前。
4. 为什么补偿点指向 `index` 而不是 `precheck`？—— 后者只判定，不修复。
5. 为什么变异测试不能省？—— 不做，你不知道断言有没有在检查。

五题都能不看手册答出来，这一套就算会了。剩下的只是把它搬到真项目上。
